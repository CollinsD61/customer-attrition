# ADR 004: Use S3 as the Data Lake, Offline Store, and Artifact Store

## Status

Accepted

## Context

The platform needs durable, cheap storage for large, mostly-write-once data:
raw customer data, processed data, feature tables, and MLflow model artifacts.
This storage must also serve as the Feast **offline store**, meaning it needs to
support the batch reads Feast's historical retrieval performs.

## Decision

Use **S3** as the single storage layer for:

- Raw data
- Processed data
- Feature tables (Feast offline store)
- MLflow artifacts (models, plots, any files logged during training)

S3 is not used for anything that needs low-latency point lookups (that's Redis's
job) or structured relational metadata (that's PostgreSQL's job — see ADR 006).

## Alternatives considered

| Option | Why not chosen |
|---|---|
| A relational database for feature tables | Poor fit for large columnar feature tables and cheap long-term retention; S3 + Parquet is the standard pattern for offline feature stores |
| HDFS / self-hosted data lake | Unnecessary operational overhead for our scale; S3 (or an S3-compatible store) is simpler to run and matches what `kind`/local dev and most cloud targets support |
| Separate storage systems per data type (e.g. one for raw data, another for artifacts) | Adds operational surface area for no real benefit at this scale; a single bucket with clear prefixes (raw/processed/features/artifacts) is easier to reason about and secure |

## Consequences

- S3 becomes a hard dependency for both the Data Pipeline and the Train Pipeline
  — if S3 is unavailable, both stop working, but the Deploy Pipeline and the
  live serving path are unaffected (they depend on the Model Registry and Redis
  respectively, not S3 directly).
- Bucket layout and lifecycle policies (e.g. cleaning up old raw data) need to
  be defined and documented — do not commit raw or processed datasets to Git;
  small samples only belong in `data/samples/` or `tests/fixtures/`.
- Every write path (Data Pipeline, MLflow artifact logging) must avoid
  hard-coded bucket names — read them from configuration (per AGENTS.md code
  conventions).
